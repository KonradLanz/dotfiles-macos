# .ai helper architecture notes

## Recommendation

Start lightweight. Do not begin with a full Python MCP server unless a repo truly needs live tool endpoints, indexing, or multi-command orchestration.

## Suggested phases

### Phase 1: shell-first
- `mcp-filelist.sh`
- `ai-bootstrap.sh`
- `ai-diff.sh`
- `ai-checksum.sh`
- repo-local `.ai/` directory with cached state files

### Phase 2: small Python helpers
Add Python only for tasks that benefit from structured parsing or state handling:
- fast checksum manifests
- SQLite cache/state
- JSON summaries
- binary-change detection for generated artifacts

### Phase 3: Python MCP server
Use a Python MCP server only when the repo needs:
- callable tools over stdio,
- richer querying than shell output,
- indexed retrieval/search,
- multi-chat shared local state with commands like `where_did_we_stop`, `what_changed`, `get_context`.

## Proposed `.ai/` layout

```text
.ai/
  context.md
  ignore
  watch-policy.json
  state.json
  sessions/
  checksums/
  manifests/
  cache/
```

## Suggested state model

- `context.md`: human-maintained repo summary
- `ignore`: repo-local exclusions
- `watch-policy.json`: file types and paths worth tracking
- `state.json`: last successful bootstrap, last active area, latest summaries
- `checksums/`: crc32 or sha256 manifests for generated/binary files
- `sessions/`: optional per-topic notes for parallel chats
- `cache/`: derived summaries that can be reused

## Recommendation for dotfiles-macos

Use shell scripts plus small Python utilities first. This is lighter than the Python MCP setup used around `eudi-nexus`, whose stack already includes `fastmcp` and other Python dependencies for indexing and server behavior.
